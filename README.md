# Task Tracker API

A simple Task Tracker REST API built with **FastAPI** and **SQLite**, containerized with **Docker**, and deployed to an **AWS EC2** instance via a fully automated **GitHub Actions CI/CD pipeline**.

This project was built as a hands-on learning exercise to understand the complete DevOps loop: **code → build → ship → run**, end to end, with zero manual deployment steps once set up. If you're setting up your very first CI/CD pipeline, this repo (and this README) walks through every step that was actually taken to get here — including the mistakes.

---

## What this API does

A basic CRUD (Create, Read, Update, Delete) task manager:

| Method | Endpoint         | Description                    |
|--------|------------------|--------------------------------|
| GET    | `/health`        | Health check (status, version, timestamp) |
| POST   | `/tasks`         | Create a new task              |
| GET    | `/tasks`         | List all tasks                 |
| GET    | `/tasks/{id}`    | Get a single task by ID         |
| PUT    | `/tasks/{id}`    | Update / mark a task done       |
| DELETE | `/tasks/{id}`    | Delete a task                   |

Interactive API docs are auto-generated by FastAPI at `/docs` once the app is running.

## Tech Stack

- **FastAPI** — Python web framework (auto docs, request validation via Pydantic)
- **SQLAlchemy** — ORM, used so the database can be swapped (e.g. SQLite → Postgres) with minimal code changes
- **SQLite** — lightweight file-based database (fine for learning/small projects; not intended for production scale)
- **Docker** — containerizes the app so it runs identically anywhere
- **GitHub Actions** — CI/CD: builds the image, pushes it to Docker Hub, and deploys it to EC2 automatically on every push to `main`
- **AWS EC2** — hosts the running container (Ubuntu 22.04, t2/t3.micro — free-tier eligible)

## Running Locally (without Docker)

```bash
# Clone the repo
git clone https://github.com/<your-username>/task-tracker-api.git
cd task-tracker-api

# Create and activate a virtual environment
python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # macOS/Linux

# Install dependencies
pip install -r requirements.txt

# Run the app
uvicorn main:app --reload
```

Visit:
- `http://127.0.0.1:8000/health`
- `http://127.0.0.1:8000/docs`

## Running with Docker (locally)

```bash
docker build -t task-tracker-api .
docker run -d -p 8000:8000 --name task-tracker task-tracker-api
```

Then visit `http://localhost:8000/health`.

Useful commands:
```bash
docker logs task-tracker      # view logs
docker ps                     # list running containers
docker stop task-tracker      # stop it
docker rm task-tracker        # remove it
```

## Deploying to AWS EC2 (manual, first-time setup)

This is the one-time manual setup done before automating with CI/CD. If you're deploying your own copy for the first time, do this once:

1. **Launch an EC2 instance**
   - AMI: Ubuntu 22.04 LTS (free-tier eligible)
   - Instance type: t2.micro / t3.micro (free-tier eligible)
   - Create a new key pair (`.pem`) — download it, you can't get it again later
   - Security group: allow **port 22** (SSH) from *My IP*, and **port 8000** from *Anywhere* (0.0.0.0/0)

2. **SSH in and install Docker**
   ```bash
   ssh -i your-key.pem ubuntu@<EC2_PUBLIC_IP>

   sudo apt update
   sudo apt install -y docker.io
   sudo systemctl start docker
   sudo systemctl enable docker
   sudo usermod -aG docker $USER
   # log out and back in for the group change to apply
   ```

3. **Push your image to Docker Hub** (from your local machine)
   ```bash
   docker login
   docker tag task-tracker-api yourusername/task-tracker-api:v1
   docker push yourusername/task-tracker-api:v1
   ```

4. **Pull and run on EC2**
   ```bash
   docker pull yourusername/task-tracker-api:v1
   docker run -d -p 8000:8000 --name task-tracker yourusername/task-tracker-api:v1
   ```

5. Visit `http://<EC2_PUBLIC_IP>:8000/health` — if you see a JSON response, it's live.

## CI/CD Pipeline (GitHub Actions)

Every push to `main` automatically:

1. Checks out the code
2. Builds the Docker image
3. Tags it with the commit SHA (so every deployed image is traceable to an exact commit — no more guessing which version is live)
4. Pushes it to Docker Hub
5. SSHs into the EC2 server, pulls the new image, stops/removes the old container, and starts the new one

The workflow lives at `.github/workflows/deploy.yml`.

### Required GitHub Secrets

Set these under **Repo → Settings → Secrets and variables → Actions**:

| Secret name           | Value                                                              |
|------------------------|---------------------------------------------------------------------|
| `DOCKERHUB_USERNAME`  | Your Docker Hub username                                            |
| `DOCKERHUB_TOKEN`     | A Docker Hub **access token** (Account Settings → Security), not your password |
| `EC2_HOST`            | Your EC2 instance's public IP address                               |
| `EC2_SSH_KEY`         | The full contents of your `.pem` private key file                   |

**Never commit these values into the repo** — that's exactly what secrets are for.

### Workflow file

```yaml
name: Build and Deploy

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/task-tracker-api:${{ github.sha }}

      - name: Deploy to EC2
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ubuntu
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            docker pull ${{ secrets.DOCKERHUB_USERNAME }}/task-tracker-api:${{ github.sha }}
            docker stop task-tracker || true
            docker rm task-tracker || true
            docker run -d -p 8000:8000 --name task-tracker ${{ secrets.DOCKERHUB_USERNAME }}/task-tracker-api:${{ github.sha }}
```

Once these secrets are set and this file is pushed, every future `git push` to `main` deploys automatically — no manual SSH, no manual `docker pull`, no manual restart.

## A real mistake made along the way (kept here on purpose)

While adding a `version`/`checked_at` field to `/health`, the deploy succeeded (green checkmark in Actions) but the live endpoint returned a `500 Internal Server Error`. The cause: `datetime` was used in the code without being imported.

**Lesson:** a green CI/CD pipeline only proves the *build and deploy steps* succeeded — it doesn't mean the *application code* is bug-free, especially for code paths not covered by automated tests. The fix was found immediately via:

```bash
docker logs task-tracker
```

which showed the exact Python traceback. This is why `docker logs` (or your platform's equivalent) is always the first move when something is live but broken — check the logs before guessing.
